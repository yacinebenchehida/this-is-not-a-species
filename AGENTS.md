# Instructions for AI coding assistants

This is a personal, playful, non-research science animation website. Prioritise attractive visuals, delightful animations, accessibility, maintainability, and correctness of stated scientific assumptions.

## Architecture
- Static GitHub Pages site. Plain HTML, CSS, vanilla JavaScript first.
- No backend, accounts, tracking, or build pipeline.
- One theme folder per scientific discipline under `simulations/`.
- Each interactive animation should have its own folder and files. Document the assumptions of any scientific model it implements.
- Keep navigation, colours and reusable styling in `shared/`; avoid breaking existing pages.
- Use relative URLs so site works at GitHub Pages project subpath.
- Do not add heavy dependencies without a clear reason.

## Scientific integrity
- These are playful animations, not validated research software.
- Explain whether animated organisms are actual agents or just representations of numerical dynamics.
- Provide automated numerical sanity checks for each implemented scientific model.
- Never describe a placeholder or illustrative animation as a validated scientific simulation.

## Collaboration
- Human owner tests functionality, scientific behaviour and aesthetics, not source code line by line.
- Make small, reversible commits; don't change unrelated animations.
- Preserve visual consistency with the homepage.
- Clearly distinguish complete features from placeholders.
- Optimise interactive animations for laptop viewing. Phone and tablet optimisation is secondary and must not compromise the laptop experience. Respect reduced-motion settings.

## Approved visual identity
- Follow the approved illustrated homepage: warm ivory paper, charcoal/navy ink, coral/orange, teal, botanical green and ochre. Serif headings and self-hosted La Belle Aurore handwritten branding.
- The homepage keeps the illustrated natural-history landscape and its original theme/featured artwork. Inner galleries and exhibit pages use the simple cartoon collection in `assets/illustrations/cartoons/`: rounded characters, clear allele markers, flat colours and sparse scenery. Scientific schematics are precise, editable SVGs in the same palette. Never substitute emoji, crude stand-ins or ornate poster scenes for the inner-page artwork.
- `butterfly-mule.png` is the official header/footer logo. `evolutionary-tree.png` is retained as a source asset and is not shown as a large page decoration. The homepage hero contains an introduction and actions over the landscape, without a large repeated wordmark or a standalone tree. Keep the introduction as real HTML text. Never use the entire flattened reference as the webpage.
- Maintain one row of five theme cards at desktop widths, responsive reflow, and three featured preview cards.

## Shared page authoring
- Current committed HTML is generated by the optional `scripts/build_pages.py` helper, which owns the shared header/footer, homepage, About, theme gallery and preview templates. No build is required in production. Regenerate and commit HTML after template changes.
- Shared presentation lives in `shared/styles.css`; progressive mobile menu behavior lives in `shared/app.js`. Preserve usable navigation without JavaScript, visible focus, Escape handling, and reduced-motion support.
- Theme folders: evolution, population-genetics, ecology, genomics, bioinformatics. Each interactive animation has an independent nested folder; cross-theme links should target the same implementation.
- Mark previews Coming soon. Catalogue records with `interactive: true` use their own `illustration.html` fragment and show an active exploration link. Do not add fake controls to previews.
- Code is AI-generated or AI-assisted and is not manually audited by the owner. Document scientific assumptions and add automated numerical tests when implementing each model.
- Before publishing a visual change, inspect it in a real browser at laptop widths; check links, fonts, artwork, missing assets, overflow, and console errors. Publish to the existing GitHub Pages URL and preserve its deployment settings.

## Inner-page artwork
- Cartoon characters share soft teal outlines, dot eyes, warm ivory space, and teal/coral/yellow/green fills. Keep important biological differences legible at thumbnail size.
- Predator characters use playful open mouths and a dining fork and knife; keep the tone friendly and comic.
- `scripts/build_schematics.py` regenerates static sequence, chromosome and ancestry SVG previews. These are static illustrations without interactive behaviour.
- Keep the shared site typography and colours. Inner galleries use plain introductions and simple cards, without large scenic banners.

## Duck Pond visual direction
- Prioritise visual appeal and engaging movement: simple rounded ducks with the same yellow body colour and teal outlines, gently moving water, one or two water lilies, and an irregular bank or sandy pond edge.
- Use code-native Canvas 2D ducks matching the simple original duck-pond illustration, swimming and turning with water trails; the bank uses simple sand and grass shapes, with two water-lily pads. Cache the sprites and background; cap drawing at 30 fps.
- Ducks swim throughout the safe pond area, including the centre, independently of generation speed, with gentler swimming as population size grows. Detailed generation sequences take 16, 8, 4 or 2 seconds; default 8 seconds.
- Allele colours carry the genetic information without letter labels. Keep their meaning clear through a simple legend. Bills are ochre so coral only ever means an allele; allele beads sit on the wing; swimming ducks have a waterline, ripple ring and reflection; faded ducks keep full-strength beads.
- The sidebar chart keeps earlier runs with the same settings as faint lines, shows mixed ducks against their expected decline, and a tally of fixed outcomes. Fixation shows a card over the pond. The many-ponds section (`replicates.js`) compares replicate ponds.
- Slow playback uses the approved shaded duck character for one close-up courtship (N ≤ 24), then shows every other duckling's own mating in turn: parents pair up, one heart and a dashed link between them, one bead from each parent into a duckling that heads for the nest. A "Watch every mating" option (up to 24 ducks) sets the generation length from the pond size (6 s close-up + 2.2 s per duckling + 3 s) so matings run one at a time and parents meet beak to beak; keep overlapping meetings out of other modes, which would herd ducks into the centre. Neutral duckling counters (Watch every mating mode only), snoring dozers, waddling ducklings and a watching frog are decorative; never reward frequent parents with prizes, which would imply selection. Hearts only ever link the two parents of one duckling (or sit over one duck for a one-parent draw); never float hearts over single chosen ducks. Ducks that passed on nothing turn grey and doze before the swap. The panel under the pond shows the gene pool (2N copies) above a nest of N places, with lines from each duckling's copies to their sources; replace adults only after the nest is full. Fast playback skips matings and shows no hearts while preserving every numerical generation. Population controls support up to 500 ducks, all drawn, and speed controls up to 100 generations per second. Keep movement independent of inheritance.

## Duck family motion study
- `motion.html` is an isolated two-parent inheritance story, generated from `motion-fragment.html`. It does not replace the population animation.
- `duck-character.js` preserves the original rounded cartoon silhouette and proportions (a flatter, wider version was tried and rejected), with a short rounded bill, a dot eye with a white sparkle, a soft cheek blush, a head outline that continues under the bill to the chest, and a teal outline. Use the same yellow body for all ducks so colour cannot imply male/female classes; only the two allele dots encode genetic information. Add gentle volume with soft lighting within that outline; do not substitute rubber-duck ellipsoids or change the reference character. Chest, head and wing poses remain articulated. `motion.js` owns wandering, courtship, copied allele trails, cloud overlap and offspring reveal.
- `family-model.js` samples one copy independently from each specified diploid parent. Replay and scrubbing preserve the draw; Another duckling samples again. Run `node --test tests/duck-family.test.cjs` after changing inheritance.

## Exhibit catalogue
- `content/exhibits.json` is the single catalogue of titles, concepts, descriptions, intended controls, artwork and theme membership. The page generator reads it to create cards and canonical exhibit pages.
- An exhibit has one primary `theme` and folder, and can appear in additional `themes` without duplicating its page or future implementation. Preserve existing exhibit URLs.
- The catalogue at `simulations/index.html` lists each exhibit once, grouped by its primary theme. The homepage features three selected exhibits.
- Implemented animations own their model, interface, styles and assumptions inside their canonical folder. The Duck Pond is interactive; the other 19 animations remain previews. Do not turn preview control labels into inactive form controls.

## Repository maintenance
- GitHub Pages publishes the committed static files from `main`; preserve the existing project URL and deployment settings.
- `index.html` is the homepage; `about/` contains the project introduction. `assets/fonts/` contains the self-hosted font and its license. Illustration roles and provenance are documented in `assets/illustrations/README.md`.
- To edit the shared page templates, update `scripts/build_pages.py`, run `python3 scripts/build_pages.py`, and commit the generated HTML. Serve the repository with a static HTTP server for local review. Production needs no Python runtime or build command.

## Editorial scope
- Call the collection “interactive animations” in descriptions and “Animations” in navigation, headings and buttons. Use “illustration” for static artwork and “model” for the numerical rules; keep public wording natural in context. Keep existing `simulations/` URLs stable; terminology does not require changing paths or identifiers.
- Write the root README and website for visitors: explain the project, what they can explore, and relevant limitations.
- Keep architecture, publishing instructions, asset preparation and maintenance guidance in developer documentation.
- Public copy should describe the project itself, without narrating design approvals, implementation history or conversations with the owner. Do not add progress reports about galleries being available or features being built. Put availability labels beside the affected illustrations; the About page explains purpose, not project status.
- Describe unfinished functionality clearly when it affects a visitor's expectations. Keep code comments focused on behavior, assumptions and reasons for non-obvious choices.

## English and French
- English pages are generated by `scripts/build_pages.py`; French pages and presentation scripts are generated by `scripts/build_locales.py` from the same sources and `content/locales/fr.json`. Run the main generator after edits. Never edit `fr/` output directly.
- Keep the project name “This is not a species.” unchanged in both languages. Translate all visitor-facing text, control states, SVG/canvas labels, accessibility labels and page metadata. Keep code identifiers, URLs, CSS classes and the numerical model stable.
- The locale builder translates exact literal text ranges, without runtime DOM observers or changes to scientific sampling. New static text without a French translation fails the build. Review new dynamic presentation strings and French grammar across interpolation boundaries.
- EN/FR links must open the equivalent page; French internal links stay French. Shared raster artwork, fonts, character rendering and numerical models are reused. User-facing READMEs have French counterparts; maintenance instructions and code comments may remain English.
